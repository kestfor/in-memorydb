## 1. Раздел 3.5 — Поведение кластера Lume при репликации

**Цель:** оценить overhead gossip-репликации на задержку и throughput записи, измерить скорость конвергенции.

### 1.1 Overhead gossip-репликации (throughput + latency)

Сравнить производительность одного узла Lume с тем же узлом в составе кластера. Нагрузка подаётся на один узел, остальные получают обновления через gossip.

**Конфигурации кластера:**

| Эксперимент | Узлов | CPU/узел | WAL | gossip interval | fanout |
|---|---|---|---|---|---|
| baseline | 1 | 4 | off | — | — |
| cluster-2 | 2 | 4 | off | 10s | 3 |
| cluster-3 | 3 | 4 | off | 10s | 3 |
| cluster-5 | 5 | 4 | off | 10s | 3 |

**Инструмент:** `lume-bench`

```bash
# baseline: один узел, SET, высокая конкурентность
./lume-bench -p 8081 -c 50 -r 4 -t set --pool-size 100000 -d 60 -w 10

# cluster-3: тот же тест, но узел — часть кластера из 3
./lume-bench -p 8081 -c 50 -r 4 -t set --pool-size 100000 -d 60 -w 10

# аналогично для GET
./lume-bench -p 8081 -c 50 -r 4 -t get --pool-size 100000 -d 60 -w 10
```

**Собираемые метрики:** QPS, p50, p90, p99 для каждой конфигурации.

**Ожидаемый результат для ВКР:** таблица «Overhead репликации» — процент деградации throughput и роста latency при добавлении узлов.

**Подготовка инфраструктуры:**
- Раскомментировать и настроить узлы в `cluster/docker-compose.yaml`
- Для 5 узлов: добавить third, fourth, fifth (шаблоны уже есть)
- Все узлы: `persistence.enabled: false`, `security.mode: disabled`, `trace.enabled: false`
- Gossip: `interval: 10s`, `fanout: 3` (стандартные значения)

### 1.2 Скорость конвергенции

Измерить, за какое время обновление, записанное на узел A, становится доступно на узле B.

**Методика:**
1. Запустить кластер из N узлов (2, 3, 5)
2. Записать ключ на узел A (`lume-cli set`)
3. В цикле читать тот же ключ с узла B, фиксируя время до первого успешного чтения
4. Повторить 100+ раз, вычислить среднее и перцентили

**Вариант реализации:** простой Go-скрипт или bash-цикл с `lume-cli` + замером `time`.

**Собираемые метрики:** среднее время конвергенции, p50, p99 (мс).

**Ожидаемый результат для ВКР:** график/таблица зависимости времени конвергенции от размера кластера.

### 1.3 Масштабирование throughput в кластере (чтение)

Нагрузка распределяется по нескольким узлам — проверить, растёт ли суммарный GET throughput при добавлении узлов.

```bash
# 1 узел: вся нагрузка на один порт
./lume-bench -p 8081 -c 50 -r 4 -t get --pool-size 100000 -d 60

# 3 узла: нагрузка распределена по трём портам
./lume-bench -p 8081 -p 8082 -p 8083 -c 17 -r 4 -t get --pool-size 100000 -d 60
```

**Ожидаемый результат:** суммарный throughput чтения должен расти линейно (full replication = каждый узел содержит все данные).

### 1.4 Горизонтальное масштабирование: линейный рост суммарного throughput

**Цель:** доказать, что при добавлении узлов в кластер суммарная пропускная способность растёт почти линейно, а задержки не деградируют значимо. Это ключевое свойство leaderless-архитектуры с полной репликацией: каждый узел обслуживает запросы самостоятельно, gossip-overhead не является узким местом.

**Ключевая идея:** использовать урезанные ресурсы на каждый узел (1 CPU), чтобы потолок одного узла был низким и эффект масштабирования был хорошо виден. Каждый lume-bench нагружает ровно один узел до насыщения — bottleneck на стороне клиента, а не сервера.

**Этап 0 — Калибровка (одноузловой baseline).**

Развернуть один узел Lume с ограничением 1 CPU. Через решётку c × r (тест 3.5) или сокращённый набор найти параметры, при которых узел выходит на плато:

```bash
# Быстрая калибровка на 1 CPU
./lume-bench -p 8081 -c 5  -r 1 -t set --pool-size 100000 -d 30 -w 5
./lume-bench -p 8081 -c 10 -r 1 -t set --pool-size 100000 -d 30 -w 5
./lume-bench -p 8081 -c 10 -r 2 -t set --pool-size 100000 -d 30 -w 5
./lume-bench -p 8081 -c 20 -r 1 -t set --pool-size 100000 -d 30 -w 5
./lume-bench -p 8081 -c 20 -r 2 -t set --pool-size 100000 -d 30 -w 5
./lume-bench -p 8081 -c 25 -r 2 -t set --pool-size 100000 -d 30 -w 5
```

Выбрать пару (c*, r*), при которой throughput на плато и p99 не деградирует катастрофически. Обозначим throughput одного узла как **T₁** и его p50/p99 как **L₁**.

**Этап 1 — Масштабирование.**

Развернуть кластер из N узлов (N = 1, 2, 3, 5), каждый с ограничением 1 CPU. Запустить N **независимых** процессов lume-bench, каждый нагружает ровно один узел с параметрами (c*, r*).

```bash
# === N = 1 ===
./lume-bench -p 8081 -c $C -r $R -t set --pool-size 100000 -d 60 -w 10 -n "scale_1node_set"

# === N = 2 === (два процесса параллельно)
./lume-bench -p 8081 -c $C -r $R -t set --pool-size 100000 -d 60 -w 10 -n "scale_2node_A_set" &
./lume-bench -p 8082 -c $C -r $R -t set --pool-size 100000 -d 60 -w 10 -n "scale_2node_B_set" &
wait

# === N = 3 === (три процесса параллельно)
./lume-bench -p 8081 -c $C -r $R -t set --pool-size 100000 -d 60 -w 10 -n "scale_3node_A_set" &
./lume-bench -p 8082 -c $C -r $R -t set --pool-size 100000 -d 60 -w 10 -n "scale_3node_B_set" &
./lume-bench -p 8083 -c $C -r $R -t set --pool-size 100000 -d 60 -w 10 -n "scale_3node_C_set" &
wait

# === N = 5 === (пять процессов параллельно)
./lume-bench -p 8081 -c $C -r $R -t set --pool-size 100000 -d 60 -w 10 -n "scale_5node_A_set" &
./lume-bench -p 8082 -c $C -r $R -t set --pool-size 100000 -d 60 -w 10 -n "scale_5node_B_set" &
./lume-bench -p 8083 -c $C -r $R -t set --pool-size 100000 -d 60 -w 10 -n "scale_5node_C_set" &
./lume-bench -p 8084 -c $C -r $R -t set --pool-size 100000 -d 60 -w 10 -n "scale_5node_D_set" &
./lume-bench -p 8085 -c $C -r $R -t set --pool-size 100000 -d 60 -w 10 -n "scale_5node_E_set" &
wait
```

Повторить всё с `-t get`.

**Конфигурация кластера:**

```yaml
# Каждый узел: 1 CPU, WAL off, gossip включён
cpus: "1.0"
engine:
  shards_num: 256
persistence:
  enabled: false
gossip:
  interval: 10s
  fanout: 3
```

Перед запуском бенчмарков — предзагрузка ключей на один узел, ожидание конвергенции по всему кластеру (для GET-тестов).

**Собираемые метрики:**

| Узлов (N) | QPS узла A | ... | QPS узла N | Σ QPS | Σ QPS / (N × T₁) | p50 (avg) | p99 (max) |
|---|---|---|---|---|---|---|---|
| 1 | | | | | 1,00 | | |
| 2 | | | | | ? | | |
| 3 | | | | | ? | | |
| 5 | | | | | ? | | |

Ключевая метрика: **Σ QPS / (N × T₁)** — коэффициент масштабирования. При идеальном линейном масштабировании = 1,00. Допустимая деградация: > 0,90 (менее 10 % overhead от gossip).

**Что может вызвать отклонение от линейного масштабирования:**
- Gossip-отправка: каждый узел отправляет обновления fanout=3 соседям → при N=5 каждый узел получает обновления от всех остальных
- CPU, потраченный на приём и применение чужих обновлений (CRDT merge)
- Сетевой трафик между контейнерами
- При N > fanout — не все узлы получают обновления в первом раунде, антиэнтропия компенсирует

**Ожидаемый результат для ВКР:**
- График: суммарный throughput vs число узлов (ожидается близко к линейному)
- График: p50 и p99 каждого узла vs число узлов (ожидается слабый рост)
- Таблица с коэффициентом масштабирования
- Вывод: gossip-overhead при N ≤ 5 не является bottleneck, масштабирование close-to-linear

**Важные нюансы:**
- Ресурсы хост-машины: убедиться, что хост имеет ≥ N+1 ядер (N узлов + N бенчмарков). Если ядер недостаточно, бенчмарки будут конкурировать с узлами за CPU и результаты будут некорректны. Альтернатива — запускать бенчмарки с другой машины.
- Сеть: все контейнеры в bridge-сети Docker. Для чистоты можно использовать host networking.
- Предзагрузка для GET: записать ключи на один узел, подождать ~30с (≥ 2 полных цикла антиэнтропии по 4 бакета × 5с = 20с), затем проверить наличие ключей на всех узлах.

## 2. Раздел 3.6 — Устойчивость к отказам

**Цель:** продемонстрировать поведение кластера при отказе узла и восстановление через WAL + антиэнтропию.

### 2.1 Отказ узла: поведение кластера

**Сценарий:**
1. Запустить кластер из 3 узлов
2. Подать нагрузку на узел A (`lume-bench`)
3. Во время нагрузки: `docker stop` узел B
4. Зафиксировать: продолжает ли узел A обслуживать запросы, есть ли всплеск latency
5. Через 30с: `docker start` узел B
6. Зафиксировать: время до возврата B в членство (SWIM detection)

**Собираемые метрики:**
- Непрерывность обслуживания (ошибок 0 / > 0 при отказе не-целевого узла)
- Задержка обнаружения отказа SWIM (секунды)
- Задержка возврата в членство после рестарта (секунды)

### 2.2 Восстановление из WAL

**Сценарий:**
1. Кластер из 3 узлов, **WAL включен** (`persistence.enabled: true`)
2. Записать N ключей на узел A
3. `docker kill` узел A (имитация аварийного завершения, без graceful shutdown)
4. `docker start` узел A
5. Замерить время от старта процесса до готовности gRPC (health check OK)
6. Проверить: все ли ключи восстановлены корректно

**Конфигурация WAL для тестов:**

| Параметр | Значение |
|---|---|
| flush_interval | 1s |
| sync_mode | false (async) |
| batch_size | 1000 |
| segment_threshold | 10000 |

**Варианты объёма данных:**
- 10 000 ключей (маленький)
- 100 000 ключей (средний — как в comparison тестах)
- 500 000 ключей (большой)

**Собираемые метрики:**
- Время восстановления (секунды) для каждого объёма
- Количество восстановленных ключей (проверка полноты)

### 2.3 Антиэнтропийная синхронизация после переподключения

**Сценарий:**
1. Кластер из 3 узлов, WAL **отключен** (чтобы изолировать эффект антиэнтропии)
2. `docker stop` узел C
3. Записать M новых ключей на узлы A и B (через lume-bench)
4. `docker start` узел C (C стартует с пустым состоянием)
5. Замерить время, пока узел C не получит все M ключей через антиэнтропию

**Контрольные точки:** периодически читать ключи с C, считать процент синхронизированных.

**Параметры антиэнтропии:** `anti_entropy_interval: 5s`, 4 бакета — полный цикл 20с.

**Собираемые метрики:**
- Время полной синхронизации (секунды) для M = 1000, 10 000, 100 000 ключей
- Динамика: % синхронизированных ключей по времени

## 3. Дополнительные эксперименты с lume-bench

Эксперименты для обогащения анализа в разделе 3.7 и демонстрации характеристик системы.

### 3.1 Влияние размера значения на latency

**Цель:** оценить, как размер payload влияет на задержки (сериализация, передача по сети, GC-давление).

```bash
# 64 байта
./lume-bench -c 50 -r 4 -t set --req-size 64 --pool-size 100000 -d 60

# 256 байт (≈ текущий comparison тест)
./lume-bench -c 50 -r 4 -t set --req-size 256 --pool-size 100000 -d 60

# 1 КБ
./lume-bench -c 50 -r 4 -t set --req-size 1024 --pool-size 100000 -d 60

# 4 КБ
./lume-bench -c 50 -r 4 -t set --req-size 4096 --pool-size 100000 -d 60

# 16 КБ
./lume-bench -c 50 -r 4 -t set --req-size 16384 --pool-size 100000 -d 60
```

**Ожидаемый результат:** таблица/график throughput и p99 vs размер значения.

### 3.2 Влияние размера пула ключей (контентность шардов)

**Цель:** показать влияние числа уникальных ключей на параллелизм (больше ключей → меньше коллизий на шардах).

```bash
# 100 ключей — высокая контентность
./lume-bench -c 50 -r 4 -t mixed --pool-size 100 -d 60

# 1 000 ключей
./lume-bench -c 50 -r 4 -t mixed --pool-size 1000 -d 60

# 10 000 ключей
./lume-bench -c 50 -r 4 -t mixed --pool-size 10000 -d 60

# 100 000 ключей
./lume-bench -c 50 -r 4 -t mixed --pool-size 100000 -d 60

# 1 000 000 ключей
./lume-bench -c 50 -r 4 -t mixed --pool-size 1000000 -d 60
```

**Ожидаемый результат:** throughput растёт с увеличением пула до определённого порога, затем стабилизируется.

### 3.3 Mixed workload (70/30 read/write)

**Цель:** измерить производительность в реалистичном сценарии смешанной нагрузки.

```bash
./lume-bench -c 50 -r 4 -t mixed --pool-size 100000 -d 60
./lume-bench -c 100 -r 2 -t mixed --pool-size 100000 -d 60
./lume-bench -c 200 -r 1 -t mixed --pool-size 100000 -d 60
```

**Ожидаемый результат:** throughput между чистым GET и чистым SET, ближе к GET (70% чтений).

### 3.5 Решётка конкурентности (c × r): точка насыщения

**Цель:** найти точку насыщения узла, определить оптимальное соотношение числа соединений (`-c`) и параллельных RPC на соединение (`-r`), оценить деградацию задержек при перегрузке.

**Параметр:** `total workers = c × r`. Решётка подобрана так, чтобы при разных комбинациях c и r получать одинаковое суммарное число воркеров, а также выходить за точку насыщения.

**Решётка для SET:**

| c \ r | 1 | 2 | 4 | 8 | 16 |
|---|---|---|---|---|---|
| **1** | 1 | 2 | 4 | 8 | 16 |
| **5** | 5 | 10 | 20 | 40 | 80 |
| **10** | 10 | 20 | 40 | 80 | 160 |
| **25** | 25 | 50 | 100 | 200 | 400 |
| **50** | 50 | 100 | 200 | 400 | 800 |
| **100** | 100 | 200 | 400 | 800 | 1600 |

*Значения в ячейках — суммарное число воркеров (c × r).*

```bash
# Общие параметры для всех запусков
COMMON="--pool-size 100000 -d 60 -w 10"

# Строка c=1
./lume-bench -c 1  -r 1  -t set $COMMON
./lume-bench -c 1  -r 2  -t set $COMMON
./lume-bench -c 1  -r 4  -t set $COMMON
./lume-bench -c 1  -r 8  -t set $COMMON
./lume-bench -c 1  -r 16 -t set $COMMON

# Строка c=5
./lume-bench -c 5  -r 1  -t set $COMMON
./lume-bench -c 5  -r 2  -t set $COMMON
./lume-bench -c 5  -r 4  -t set $COMMON
./lume-bench -c 5  -r 8  -t set $COMMON
./lume-bench -c 5  -r 16 -t set $COMMON

# Строка c=10
./lume-bench -c 10 -r 1  -t set $COMMON
./lume-bench -c 10 -r 2  -t set $COMMON
./lume-bench -c 10 -r 4  -t set $COMMON
./lume-bench -c 10 -r 8  -t set $COMMON
./lume-bench -c 10 -r 16 -t set $COMMON

# Строка c=25
./lume-bench -c 25 -r 1  -t set $COMMON
./lume-bench -c 25 -r 2  -t set $COMMON
./lume-bench -c 25 -r 4  -t set $COMMON
./lume-bench -c 25 -r 8  -t set $COMMON
./lume-bench -c 25 -r 16 -t set $COMMON

# Строка c=50
./lume-bench -c 50 -r 1  -t set $COMMON
./lume-bench -c 50 -r 2  -t set $COMMON
./lume-bench -c 50 -r 4  -t set $COMMON
./lume-bench -c 50 -r 8  -t set $COMMON
./lume-bench -c 50 -r 16 -t set $COMMON

# Строка c=100
./lume-bench -c 100 -r 1  -t set $COMMON
./lume-bench -c 100 -r 2  -t set $COMMON
./lume-bench -c 100 -r 4  -t set $COMMON
./lume-bench -c 100 -r 8  -t set $COMMON
./lume-bench -c 100 -r 16 -t set $COMMON
```

**Аналогично для GET** — повторить всю решётку с `-t get`.

**Собираемые метрики (для каждой ячейки):** QPS, p50, p90, p99.

**Ожидаемые результаты и что искать:**

1. **Точка насыщения throughput** — значение c × r, после которого QPS перестаёт расти. Это потолок одного узла на 4 ядрах.

2. **c vs r при одинаковом c×r** — при фиксированном числе воркеров (напр. 100 = 50×2 = 25×4 = 10×10) throughput может различаться:
   - Больше соединений (`c↑, r↓`) → больше TCP-сокетов, выше стоимость syscall, но HTTP/2-мультиплексирование не перегружено.
   - Меньше соединений (`c↓, r↑`) → меньше сокетов, но больше мультиплексированных RPC на одном соединении → возможна head-of-line блокировка в HTTP/2-потоках.

3. **Деградация за точкой насыщения** — при c×r > порога: throughput стабилизируется или падает, p99 резко растёт. Определить, при каком уровне конкурентности p99 превышает 5 мс, 10 мс.

4. **Heatmap-визуализация** — результат удобно представить как тепловую карту:
   - Ось X: r (RPC per connection)
   - Ось Y: c (connections)
   - Цвет: QPS (или p99)

**Ожидаемый результат для ВКР:**
- Таблица/heatmap throughput(c, r) и p99(c, r)
- Определение оптимальной рабочей точки (максимальный QPS при p99 < целевого порога)
- Анализ: что является узким местом — число соединений, мультиплексирование или CPU

**Цель:** количественно оценить стоимость персистентности.

| Конфигурация | WAL | sync_mode | flush_interval |
|---|---|---|---|
| no-wal | off | — | — |
| async-1s | on | false | 1s |
| async-100ms | on | false | 100ms |
| sync | on | true | — |

```bash
# для каждой конфигурации:
./lume-bench -c 50 -r 4 -t set --pool-size 100000 -d 60
./lume-bench -c 50 -r 4 -t get --pool-size 100000 -d 60
```

**Ожидаемый результат:** GET не зависит от WAL; SET деградирует с ужесточением гарантий.

## 5. Подготовка инфраструктуры

### Docker-compose для кластера

Раскомментировать/добавить узлы в `cluster/docker-compose.yaml`:
- 2 узла: first + second
- 3 узла: first + second + third
- 5 узлов: все пять

Для каждого узла:
- Уникальный `NODE_ID` (через env)
- `SEEDS` — список ранее запущенных узлов
- Единый шаблон `node-configs/template.yaml`
- Порты: 8081, 8082, 8083, 8084, 8085

### Конфигурации для WAL-тестов

Подготовить варианты YAML-конфигов:
- `wal-off.yaml` — `persistence.enabled: false`
- `wal-async-1s.yaml` — `persistence.enabled: true`, `sync_mode: false`, `flush_interval: 1s`
- `wal-async-100ms.yaml` — аналогично, `flush_interval: 100ms`
- `wal-sync.yaml` — `persistence.enabled: true`, `sync_mode: true`

### Скрипт конвергенции

Написать Go-скрипт или использовать `lume-cli`:
```bash
# Записать на узел A
lume-cli -addr localhost:8081 set convergence_test_key "value"

# Читать с узла B до получения
start=$(date +%s%N)
while ! lume-cli -addr localhost:8082 get convergence_test_key | grep -q "value"; do
  sleep 0.01
done
end=$(date +%s%N)
echo "Convergence: $(( (end - start) / 1000000 )) ms"
```
